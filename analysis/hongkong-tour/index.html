01Summary

Hong Kong Tour is a guide to 143 places in Hong Kong — Hong Kong Island, Kowloon and the New Territories — split into 27 neighbourhoods. Every entry carries a real photograph of the place, a rating, a description, practical tips, a location and (where available) a map link. Search and fifteen category filters sit on top.

The interesting part is not the content, it is the delivery. One Python core — data, launcher, HTML interface — is packaged as five installable archives (macOS .dmg, Windows .exe, Linux .deb, portable .zip, Android .apk) plus an iOS/iPadOS Xcode project and a server-less browser build. The same code renders all of them; only the shell around it differs.

Five separate bugs came out of that packaging, and every one of them produced a file that looked plausible and was actually broken. They are documented below with root causes, because they are the reusable part of this project.

03The data model

One nested dictionary: region → area → spots. Regions carry their own name, Chinese name, blurb, hero image and accent colour; areas group spots into walkable neighbourhoods.

    "description": "...", "image": "...", "color": "#1f4bd8",

Why the Chinese is inside name

The spot names embed their Chinese form ("中環 Central") while name_cn holds the Chinese alone. The interface renders both, which originally printed 中環 Central 中環 on every card — a visible bug. The fix is a shared guard rather than a second field:

function cnSuffix(name, cn) {
  return (cn && !name.includes(cn)) ? cn : '';   // '' when name already carries it
}

Used for both the area header and the spot card. This is the kind of bug that only shows up in a build where CJK actually renders, which is why the automated test now asserts the subtitle never repeats the title.

The Android and iOS builds never touch Python: they ship the HTML, CSS, JS and images, and the data arrives through the same JSON the server would have served. That keeps the APK at 2.3 MB while the desktop builds carry a whole interpreter.

05The five packaging traps

Each of these produced an artifact that passed a naive check. Each is a macOS-toolchain or hosting-limit problem, not an app problem.

1 · The .deb was 96 bytes

symptom: file exists, plausible name, no content

Cause. macOS ar is BSD ar: it prepends a __.SYMDEF / ranlib symbol table and writes BSD-style member headers. dpkg expects GNU ar. It parsed the file, found no valid members, and the archive ended up as a 96-byte stub.

Fix. build/make_deb.py writes the ar archive by hand — global magic, GNU member headers, control members stored as ./control and ./md5sums (no DEBIAN/ prefix inside the member name). Never use ar here.

2 · The Windows .exe was a Mac binary

symptom: 306 MB .exe that Windows refuses to run

Cause. The SFX was built from 7zCon.sfx as shipped by Homebrew, which is a Mach-O stub, not a Windows PE. Concatenating a Mach-O stub with a payload yields a file that still says .exe.

Fix. Pull real Windows PE stubs (7zS.sfx, 7zS2con.sfx) from the 7z920_extra package into build/sfx/, and verify the result: verify_windows_exe.py checks the MZ DOS header and the PE\0\0 signature at the e_lfanew offset before the file is allowed into dist/.

3 · The macOS app would not open

symptom: double-click does nothing, no dialog

Cause. Finder launches an .app with a minimal PATH that does not include Homebrew or pyenv, so the launcher's python3 resolved to a Python without pywebview. The process died before a window could exist.

Fix. Probe by import, not by path: the launcher walks a candidate list and takes the first interpreter where python3 -c "import webview" succeeds. A path existing is not evidence the module does.

4 · Cloudflare Pages silently deletes files over 25 MiB

symptom: deploy says success, installer URLs 404

Cause. Pages hard-caps a single asset at 25 MiB, and the deploy script prunes oversized files (find … -size +25600k -delete) before upload. A 300 MB installer simply disappears from the bundle with no error.

Fix. Keep installers out of the Pages bundle entirely.

5 · GitHub refuses the files, the site refuses the size

symptom: nowhere to put 1.2 GB of installers

Cause. The repo tree rejects any file over 100 MB; git push fails outright. Pages rejects anything over 25 MiB. Both limits are hard.

Fix. Publish the archives as GitHub release assets (2 GB per-asset limit, not part of the tree) and stream them through a small Cloudflare Worker at /files/hongkong-tour/…. The Worker forwards Range in both directions instead of buffering, so the download stays same-origin on isaac1804.com, hides the GitHub URL, and resumes when the connection drops — which matters on a school network.

06The browser build

The desktop app talks to a local server (/api/region, /api/search, /static/images/…). On a static host there is no server, so build/build_web.py removes it rather than emulating it:

  • freezes the /api/region response to data.json (111,088 B);
  • downscales and re-encodes photos with sips -Z 1200 -s formatOptions 75 — 300 MB of source images become 28 MB of shipped ones;
  • injects a search shim that indexes the frozen data client-side;
  • emits a real favicon so the page does not request a missing one.
Two bugs the static build introduced, both caught by tests:
  • The shim built its index at parse time, before loadData() had populated the data — so search returned nothing. Now the index is built lazily on first search.
  • Search results called goToSpot(spot.region_key, …), but the flattened index never set region/region_key, so jumping to a result threw. Now both are attached when each spot is indexed.

08Known gaps

One spot has no category. 林村許願樹 Lam Tsuen Wishing Trees (Tai Po, New Territories) is missing its category field, so it is invisible to every filter chip — it only appears in the unfiltered list and in search. One line of data fixes it.
The content skews to the New Territories. 73 of 143 spots (51%) are in the NT versus 38 on Hong Kong Island and 32 in Kowloon, largely because country parks and outlying islands carry many entries. Not wrong, but not balanced either.
iOS is source, not a download. The Xcode project is generated and valid, but producing an .ipa needs full Xcode plus a signing identity. This machine has Command Line Tools only, so no iOS build is claimed.
macOS first launch needs a deliberate open. The app is ad-hoc signed, so Gatekeeper blocks a plain double-click: right-click → Open, or System Settings → Privacy & Security → Open Anyway. Removing that step needs a paid Apple Developer ID and notarisation.
The desktop builds are heavy for what they do. ~300 MB each, almost entirely interpreter and webview runtime. A rewrite in a compiled stack, or shipping the browser build as a native shell (Tauri/Wails), would plausibly land under 20 MB.
Photographs are sourced from Wikimedia Commons. Suitable for a personal project with attribution, but each file's licence should be audited before any commercial use. This is the one part of the project I would not call cleared.

10Reproducing it

# run the desktop app
cd /Applications/HongKongTour && python3 hongkong_tour.py      # port 8570

# rebuild the four desktop packs + Android
cd /tmp && env -u PYTHONPATH /bin/bash \
  /Applications/HongKongTour/build/build_linux_windows.sh

Use native /bin/bash: a Homebrew bash is x86_64 and drags the build into Rosetta, where xcrun and the SDK disagree. Unset PYTHONPATH when calling the scripts — a stale PIL in a venv breaks the image step otherwise.

# verify every pack
env -u PYTHONPATH python3 /Applications/HongKongTour/build/verify_all_packs.py

# rebuild the static browser build
env -u PYTHONPATH python3 /Applications/HongKongTour/build/build_web.py
