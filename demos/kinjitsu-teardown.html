「禁日」 — from a Preview puppet show to a real reader

The first version of this flipbook was two AppleScript applets that carried 75 photographs of pages inside their own bundles and then asked Preview — via the Accessibility API — to go full screen. This is the same book rebuilt as a web reader: one page at a time, every page at its original pixel size, with the page-turn, thumbnails, deep links and resume state the original never had.

The one-line history

The original app's entire "flipbook" was three keystrokes sent to Preview — ⌘2, ⌥⌘1, then View ▸ Enter Full Screen — wrapped in a try block that silently swallowed the failure when macOS refused the Accessibility request.

01 · What was actually in the old app

Both bundles live in /Applications/Installed Applications/. They are Script Editor applets, not compiled apps: same 15,094-byte main.scpt in each, same bundle identifier com.apple.ScriptEditor.id.test-flipbook, same displayed name "test flipbook". The only real difference is the folder of photographs each one carries.

Filename order was the reading order, and the filenames were unpadded — page 1.jpg, page 2.jpg … page 36.jpg. That survives Finder's numeric sort, but it is one sort call away from serving page 10 before page 2.

02 · The 15 KB that did all the work

1

Photos were copied into the app

On first run the script asked for image files and copied them into Contents/Resources/FlipbookPhotos/, then told you to double-click the app again. The bundle was the library: editing a page meant re-running that import.

2

Preview was reconfigured, globally

defaults write com.apple.Preview PVImageOpeningMode 1 — a persistent, machine-wide preference so that every future image you open in Preview arrives in a single window, whether or not you are looking at the flipbook.

3

Every page was opened at once

No lazy loading and no window management: 36 or 39 full images decoded up front, so the first paint waited on the heaviest page in the set.

4

System Events pressed the buttons

Three UI-scripting calls: ⌘2 (single page), ⌥⌘1 (hide sidebar), View ▸ Enter Full Screen. Everything the reader did was done by another app's menu, so anything that changed Preview's menus broke the flipbook.

03 · Why it degraded instead of failing

error "-25211" — System Events got an error: osascript is not allowed assistive access. what the script swallowed

The full-screen step sat inside try … end try with a fallback that simply zoomed the Preview window. So when Accessibility permission was missing — after an OS update, a new machine, a reset privacy database — the app still opened, just not full screen. Nothing reported a problem. That is the worst failure mode there is: it looks like the app half-worked.

What the old design cost

  • Machine state: reads and writes a global Preview preference
  • Permission debt: needs Accessibility, checked only by crashing quietly
  • Two copies: the same 15 KB script shipped twice, with the pages duplicated inside them
  • No navigation: no page number, no jump, no thumbnail, no resume
  • No sharing: you cannot link someone to page 20

What the rebuild needs

  • One static folder: index.html + 75 JPEGs + thumbnails
  • No permissions, no other app, no OS settings touched
  • Deep links: #v1p12, #v2p20
  • Resume: last page per volume, remembered locally
  • Native size: one click for 1:1 pixels, four for fit

04 · The geometry problem nobody warns you about

These are photographs of pages, so they are not one size. After the framing pass (section 07) volume 1 has 34 distinct sizes across 36 pages (378–465 wide, 539–640 tall), and volume 2 has 36 distinct sizes across 39 pages (413–1188 wide, 547–1684 tall). Aspect ratios run 0.49 → 0.82.

That single fact decides the layout. A classic two-page spread pairs leaves across a gutter, which only works if paired pages share a height; here a 378 px leaf would face a 1204 px one. So the reader shows one page at a time, sizes the stage to that page's own aspect ratio, and lets the page turn be the thing that reads as a book. No stretching and no letterbox inside a fake frame — and the one crop that does happen (section 07) removes dead black frame, never a resampled pixel.

05 · How the turn works

Two stacked layers. The front layer holds the page you are on; the back layer holds whatever is being revealed. On a forward turn the back layer is loaded with the next page and the front rotates -104° around its left edge inside a 2400 px perspective — one moving layer, one compositor-friendly transform. Going back, the incoming page starts at -104° with transitions disabled, then animates to 0°, which reads as a page sweeping back into place.

The reset is the fiddly part: after the animation ends the front layer must be restored to rotateY(0) without transitioning, or the new page visibly swings back into frame. The commit step sets transition:none, swaps the image, forces a reflow, then clears the inline style. The verification below asserts the resting transform is literally none.

Separate pass for the states: a fresh visit hides Continue reading; reading to page 3 and reloading shows Continue page 3 and lands on 3/36; aborting one image request surfaces the error panel with the exact filename (pages/v1-05.jpg) and a working retry; with prefers-reduced-motion the turn becomes a 130 ms fade and navigation still works. 07 · The white edges

Every page arrived still framed by its photograph: a black caption bar across the top (75–89 px on the 640-tall pages, 207–240 px on the large ones — about 13% of the page height), the photo's black surround down the sides, and a bright white strip where the sheet's edge caught the light. On a dark stage that reads as a pale border on some pages and a black border on others, which is exactly how it looked.

The build now takes the dead framing off. For each side it walks in while the line is still dark (mean ≤ 120), accepts the band only if the band really is black (mean ≤ 45), then removes the pure-white rim on top of that. It then refuses its own work: if more than 1.5% of the page's ink would be lost, the page is left alone. 65 of 75 pages were re-framed, median 13.9% of the frame, maximum 17.6%, and no page lost more than 0.52% of its ink. Nothing is resampled — the crop only moves the rectangles.

Where it declined

10 pages were left exactly as they were. Five are dark pages — the black title cards (10月25日 - 到訪學校, 家庭訪問日) and the night scenes — where the black is the artwork. The other five are pages whose only trim would have clipped a drawing that runs off the sheet, so the ink test vetoed it. The first version of the detector did try to re-frame v1-32 by 58.7% of its frame; that is the failure the ink test exists to stop.

08 · What this still doesn't do

Honest limits

  • The source is small. Page 1 is 451 px wide; at 1440 the reader draws it 543 px wide, so it is enlarged about 1.2× and looks it. 1:1 mode is there for exactly this.
  • The text is paint, not text. These are photographs of pages: nothing is selectable, searchable or indexed, and this Mac has no CJK OCR data installed, so I could not transcribe a single line.
  • No audio, no bookmarks, no per-page notes — none of that was in the original to preserve.

Reading decisions I made

  • One continuous book. The two volumes are chained (36 → 1) rather than kept apart, because the second bundle carries the same script and a later page set.
  • Original page files kept. The .app bundles were never modified; the build script only reads them.
  • Filenames preserved as provenance in the manifest ("src":"page 7.jpg") next to the normalised web name.

09 · Rebuild it

# 1. stage 75 pages out of the two applets, native pixel sizes, plus thumbnails + manifest
python3 ~/scripts/build-kinjitsu.py
# → v1: 36 pages, v2: 39 pages, 41.0 MB source → 8.2 MB web

# 2. take the dead framing off (black caption bar + photo surround), then re-index
python3 ~/scripts/trim-kinjitsu-pages.py --apply   # 65 of 75 pages, median 13.9% of the frame
python3 ~/scripts/reindex-kinjitsu.py              # rewrite manifest + thumbs at the new sizes

# 2. grade it in Chromium at 390 / 768 / 1440
python3 ~/scripts/verify-kinjitsu.py        # ends with "FAILURES: none"

# 3. states: resume, error, reduced motion
python3 ~/scripts/verify-kinjitsu-states.py

The reader is one HTML file with no dependencies — no framework, no build step, no network calls beyond its own images. The manifest ships as a classic <script> rather than JSON fetched over fetch(), so the book also opens correctly straight off the filesystem.
