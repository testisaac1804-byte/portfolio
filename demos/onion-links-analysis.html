How each address was tested

1

No Tor Browser assumption

Tor Browser is installed at /Applications/Installed Applications/Tor Browser.app, but a GUI proves nothing about an address. The test harness is the tor daemon that ships with it, started headless: tor --SocksPort 9050 --DataDirectory /tmp/tordata.

2

Every request goes through the onion network

curl --socks5-hostname 127.0.0.1:9050 — the hostname flag matters: it hands the .onion name to Tor to resolve, instead of trying (and failing) to DNS-resolve it locally.

3

Three signals per address, not one

HTTP status code, download size, and the page <title> scraped from the body. A 200 alone is not proof — a captive portal or a phishing clone also returns 200. Byte count plus a sane title is what makes “live” mean something.

4

Retry ladder before calling anything dead

Onion circuits on this network are slow and drop mid-handshake. Anything that failed got a second and third attempt with a longer ceiling (45 s → 90 s). Four addresses moved between runs, so a single timeout proves nothing.

5

Cross-check against an independent monitor

dark.fail publishes per-site up/down status. I compared its labels to my own results and only then treated the dead ones as dead — agreement from a second source is the difference between “my network is throttled” and “this service is offline”.

6

Ship a page that works inside Tor Browser

The deliverable is a single dark-theme HTML file with Open / Copy per row. Chrome and Safari cannot resolve .onion, so the page is meant to be dragged into Tor Browser. Every address on it is one of the 13 verified rows below.

  3. rendezvous cookie

guard + middle
  1. sees encrypted cells only
  2. no exit relay involved
  3. relay never learns the target
“no exit nodes in consensus” is fine here
onion service
  1. intro point + rendezvous
  2. answers over TLS
  3. its IP stays hidden
the last hop is the server itself

The tor log printed “The current consensus has no exit nodes. Tor can only build internal paths, such as paths to onion services.” — a warning that would break a normal website fetch, and completely irrelevant to onion fetches. For an onion service the third hop is the service, reached via a rendezvous point, so no exit relay is needed. The 5 clearnet control fetches (freedom.press, securedrop.org, signal.org, archive.org, wikipedia.org) all returned real pages, which proved circuits had capacity — so a failing .onion was the address, not the network.

What actually makes an onion link trustworthy

1 · The operator's own site

Visit bbc.com in Tor Browser and a purple “.onion available” chip appears. That is the Onion-Location header, served by the organisation itself. It is the only source that cannot be poisoned by a third party.

2 · PGP-signed lists

A published address is a claim; a signed address is a verifiable claim. dark.fail signs its list and publishes a mirror file precisely because clones outrank originals.

3 · v3 addresses are self-authenticating

The 56-char address is derived from the service's public key. You cannot typo your way onto an attacker's server — a wrong address simply goes nowhere. That is why the dead rows above fail silently instead of landing on fakes.

4 · The threat is the list, not the network

Phishing works by handing you a live clone at a similar-looking address. Ahmia itself prints “right onion address starts with juhanurmihxlp77 and ends with 4csyd.onion” for exactly this reason.

Honest limitations. Statuses are a snapshot of 20 Oct 2026 on a throttled school connection — mirrors go up and down, and “no response” here means “not proven either way”, not “dead forever”. Five of my failures (Tor Support, Debian, Mullvad, Riseup v2, DW v2) were addresses I reconstructed or that belong to the retired 16-character v2 network — my bad guesses, not broken services. The set is also deliberately narrow: news, search, email and whistleblower boxes only. No markets, no “hidden wiki”, nothing that needed a legal judgement call. And no security tool can tell you that a live onion is the right onion — that check only comes from the operator's signature or its own clearnet site.

What's next

Candidate V2 — a local checker

check-onion.sh <address> … that boots Tor, walks a list, and prints live/dead + title + bytes as a table. The harness already exists in this session (worker.sh + a parallel driver); what is missing is packaging it so it runs on demand instead of inside one chat.

Method. Headless tor daemon on 127.0.0.1:9050; every address fetched with curl --socks5-hostname; HTTP code, byte count and page title recorded per attempt; failed rows retried; results cross-checked against dark.fail's published status labels. Addresses on the shipped board come from operators' own sites and the SecureDrop JSON directory, never from a “2026 updated onion list”.
Honesty notes. Byte counts are transfer sizes, not page weights. “Live” means the service returned real content once, from here, today. One address (BBC) was wrong on my first attempt and is reported as such rather than quietly fixed.
