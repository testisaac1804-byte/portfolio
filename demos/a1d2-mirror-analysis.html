The site is not the story — the redirect is. a1d2.org#PAYLOAD navigates instantly, with no interstitial, to whatever URL the payload decodes to. Anyone can craft a payload. The only guard is an http(s) allowlist. So a link like this is a blind jump, and the site's own copy still describes a confirmation step that was deleted from the code.

01 · What is actually there

Three HTML pages, a stylesheet, and five JavaScript files. The landing page is bilingual, Chinese first (lang="zh-Hans" on the document, with an English block below), and it names exactly one project plus one way to make contact:

a1d2.org 链接压缩器 在浏览器里把长链接压短、并优化二维码，不需要后端。基于 p2r3 的开源项目 ha.mr（MIT）。 打开 → Link compressor Compress long links and optimise QR codes entirely in the browser, no backend. Based on ha.mr by p2r3 (MIT). Open → 更多陆续放上来。 / More to come. 联系 — 有事找我，发邮件：support@a1d2.org

That is the entire site. The one project is a fork of ha.mr (p2r3, MIT) — the files keep the upstream structure (compress.js, alphabets.js, main.js, lean-qr), and its own title calls it “link compressor (private)”. QR generation is lean-qr (David Evans, MIT). There is no framework, no build step, no server-side rendering: 129 KB of compression tables, 340 lines of glue, and a 7 KB QR encoder.

02 · The compressor, measured

I ran the mirror's copy of the code in a real browser and fed it four URLs. The payload travels in the fragment, so the domain is a fixed cost — compression only pays off on long links.

Three alphabets are in play. The payloads above use 84 printable ASCII characters. A second, 43-character uppercase set is reserved for QR codes, which carry the payload in the path (/q/PAYLOAD) instead of the fragment, which is why /q/anything renders the compressor rather than a 404.

The third set is the party trick: 3,953 emoji, one per entry, switched on with a UI toggle rather than a URL flag — so the mode never appears in a shared link. Decoding stays unambiguous because textAlphabets() picks the emoji table only when the payload contains a character outside the ASCII alphabet, and a byte-for-byte comparison of the two tables finds no overlap. It compresses hardest of the three and needs a phone keyboard to type.

Round-trip is lossy in exactly one way: an empty path segment before a query is dropped — https://ps.ps/?id=33 decodes to https://ps.ps?id=33. Semantically the same request for virtually every server, but worth knowing if a signature ever depends on the slash.

The decoder earns its keep, though. Because the format carries no checksum, it re-compresses what it decoded and compares against the input before trusting it:

// The format carries no checksum, so decoding with the WRONG alphabet can produce // convincing-looking nonsense (a random payload once "decoded" to a plausible youtube URL). // Re-compressing the result is the integrity check: only the correct alphabet reproduces the // payload exactly, so anything else is rejected. — /q/main.js, lines 216–219

03 · The thing I got wrong, and the comment that proves it

My first read of this site said it showed a “Proceed to <url>?” screen and that nothing was fetched until you clicked. That was wrong. It is true of upstream ha.mr, which I had read about before reading this fork's main.js. The fork deletes the interstitial, and says so in a comment:

const target = decompress(payload, alphabet); // Redirect straight through - no confirmation screen. The protocol check is not // decoration: a payload is opaque data that anyone can craft, so refuse anything // that is not http(s) instead of letting it navigate to javascript: or data: here. const url = new URL(target); if (url.protocol !== "http:" && url.protocol !== "https:") { throw new Error(`Refusing to redirect to ${url.protocol}`); } window.location.replace(url.href); return; — /q/main.js, lines 317–326

I confirmed it behaviourally rather than trusting the comment: navigating to /q/#<payload for example.com> landed on example.com, with the fragment gone and no intermediate page. location.replace also means no history entry — the back button skips the compressor entirely, so a redirected visitor cannot easily walk back to see what they clicked.

What this means practically. An a1d2.org#… link is a blind jump. The fragment is never sent to the server, so no filter, preview bot or link scanner can see where it goes — that is the privacy feature and the attack surface at the same time. The http(s) allowlist stops javascript: and data: payloads from running on the domain; it does not stop the payload from pointing at a phishing page.

The /q/stats page is where the fork's paperwork fell behind its code. It still describes the deleted step:

A link is counted when its confirmation screen appears, so pressing Stop still counted. — /q/stats, live copy

There is no confirmation screen, and main.js contains no fetch call at all — the counter was removed from the client. The endpoints agree: GET /stats.json returns the site's 404 page, and POST /a answers 405 to every method and content-type I tried. So the stats page is an orphan: a UI for a feature whose client half and server half are both gone.

04 · Privacy: what it protects and what it leaks

Genuinely private by design

  • The payload lives after #, so the destination never reaches the server — not in access logs, not in the CDN, not in a referrer
  • Compression happens in the browser; there is no API call to compress anything
  • No cookies, no localStorage of URLs, no third-party scripts except one beacon (below)
  • noindex, nofollow on all three pages, so the site is deliberately invisible

Where it leaks anyway

  • Cloudflare Web Analytics is injected into all three pages (token 410474ed…21e3), so there is a third-party request per page load
  • The beacon posts to /cdn-cgi/rum; it is cookieless, but it still records the visit
  • Once you land on the destination, that site sees a referrer of https://a1d2.org/
  • Anyone watching the URL bar (screen share, shoulder, screenshot) sees the whole payload

Correcting myself again: I earlier called this site free of third-party requests. That was wrong — the beacon is there, which is why the mirror throws a 404 for /cdn-cgi/rum whenever one of its pages loads.

05 · Where it lives — or doesn't

There is no origin IP to geolocate. Every address belongs to Cloudflare's anycast range, and the real server could be in a Shanghai flat, a Frankfurt VPS, or a static build with no origin at all — all three produce identical headers. The registrant fields are redacted to the registrar itself, and certificate transparency shows no mail., dev. or bare-IP certificate that would leak a direct-to-origin host.

Two consequences worth spelling out:

  • The contact address cannot receive mail. With no MX record, mail to support@a1d2.org falls back to the A record — Cloudflare's proxy, which does not accept SMTP. And with no SPF/DMARC, the domain can also be spoofed in mail.
  • The site is written for a Chinese-reading audience. The landing page declares lang="zh-Hans" and puts its Chinese block first, and the custom 404 page opens with 页面未找到 before “Page not found”. That is solid evidence of audience and language — the one thing this site does disclose — but it is not evidence of where the author is sitting. A site can be written in one language from anywhere on earth.

07 · Verdict

Not malicious. No obfuscation, no eval, no exfiltration, no credential form. The code is careful in ways hobby projects rarely are: a protocol allowlist before navigating, a re-compression integrity check because the format has no checksum, and everything computed client-side. Both dependencies are MIT-licensed and correctly attributed.
Also not trustworthy, in the sense that matters. The operator is anonymous by construction (proxied, redacted, noindex, dead contact address), the domain is five weeks old, and the one interaction the site offers is an instant redirect to an arbitrary URL with no preview. Treat every a1d2.org#… link as “somebody wants me to land somewhere”, decode it first, and only then decide.
Method. Fetched with a plain HTTP client; headers, TLS chain and DNS read directly; RDAP for the registration; certificate transparency for subdomains; behaviour verified by driving the mirrored copy in headless Chromium (compression, round-trip, redirect). Safety checks were passive and read-only.

Honesty notes. Two things on this page are corrections of my own first pass, and both were caught by building the mirror rather than by reading the site: there is no confirmation screen (that belongs to upstream ha.mr), and there is a third-party beacon (Cloudflare Web Analytics). “Written for a Chinese-reading audience” is quoted from the site's own markup, not an inference about a person. “Where it is hosted” is unanswerable, and saying so is the finding.
